# [NoMercy Status](https://status.nomercy.tv)

This repository contains the status page for [NoMercy Entertainment](https://nomercy.tv), powered by [Upptime](https://github.com/upptime/upptime).

Monitored today (see `.upptimerc.yml`): the website, the control plane API, the web
app, Keycloak auth, the CDN, the docs site and the package repository — seven checks,
run every five minutes.

Each check targets something only that service can serve. This matters: nomercy.tv,
api.nomercy.tv and cdn.nomercy.tv all sit behind the same Cloudflare front door, and a
bare `GET` on the apex of each returns the byte-identical page. Probing those apexes
would give three green rows that all measure the same thing, so the API is checked via
a real authenticated route, the CDN via a real asset, and auth via Keycloak's realm
document. Response-time ceilings are set per service, so a service that is reachable
but slow reports as degraded rather than up.

The media server is self-hosted by each user, so there is no instance for this page to
monitor and it is deliberately absent.

overwritten on every run.

## How the page is built

The status page is not Upptime's stock one. A generator reads
`history/summary.json` and the git history of each `history/<slug>.yml`, and
writes a landing page plus one detail page per service into `assets/`.

```
tools/build-status-site.mjs   the generator (Node, zero dependencies)
tools/lib/                    parsing, day classification, rendering
tools/assets/                 hand-written source: status.css, status.js, heroes/
assets/                       GENERATED output -- do not hand-edit
```

Upptime's own `site` command copies `assets/*` **over** its export at deploy
time, which is how this ships without modifying any Upptime-generated workflow.
`Status Site CI` regenerates daily and commits only when the output changed.

```sh
node --test tools/test/*.test.mjs   # note the glob: `node --test tools/test/` fails
node tools/build-status-site.mjs    # regenerate assets/
```

The five hero illustrations live in `tools/assets/heroes/`. All of them ship and
the page reveals one at random per load.

## Things worth knowing before you change something

**Any branch that touches `assets/` deploys to production.** Upptime's generated
`site.yml` triggers on `push` with `paths: ["assets/**"]` and no branch filter,
so pushing a work-in-progress branch that touches `assets/` publishes it to
status.nomercy.tv. This cannot be fixed here: `site.yml` is regenerated by
`upptime update-template`, which would discard any edit.

**Checks run far less often than the config says.** `.upptimerc.yml` asks for a
check every five minutes. GitHub treats `schedule` as best-effort and drops most
of them: measured over 200 runs, this repository actually saw five to seven runs
a day -- median gap 34 minutes, 90th percentile 3.7 hours, worst case 12 hours.
An outage can therefore go unnoticed for hours.

Nothing in this repository can change that; the throttling is on GitHub's side.
`uptime.yml` does also accept `repository_dispatch: types: [uptime]`, which is
not throttled, so a check can be triggered on demand:

```sh
gh api -X POST repos/NoMercy-Entertainment/nomercy-status/dispatches   -f event_type=uptime
```

**Redefining a check discards its old history, on purpose.** An observation is
only kept if it measured the URL the check points at _today_. When `API` moved
from `https://api.nomercy.tv` to `/v1/server`, the earlier observations stopped
counting -- the apex is a shared Cloudflare front door that answers for several
hostnames, so those days measured the front door, not the API. Presenting them
as API history would be a lie of exactly the kind the grey band exists to avoid.
Those days become "no monitoring data" instead, and the bar recovers as real
observations accumulate.

**The workflow files are generated.** All eight Upptime workflows are rewritten
by `update-template`; put customisations in `.upptimerc.yml` instead. Only
`status-site.yml` is hand-maintained, and its name is deliberately not one of
the eight.
